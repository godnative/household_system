# 阶段 2：目标架构与标准设计

## 1. 目标
基于阶段 1 已冻结的需求基线，完成 Web 迁移的目标架构、前后端边界、核心专题方案和统一标准定版，为阶段 3 工程骨架搭建提供稳定输入。

本阶段不是实现业务功能，而是回答以下问题：
- Web 版系统最终应采用什么样的总体形态。
- 前端与后端分别负责什么，边界在哪里。
- 认证、权限、打印、图片、数据库恢复等高风险专题如何落地。
- 阶段 3 开发时必须遵守哪些统一标准。

## 3. 当前已知缺口
- PostgreSQL 的统一本地启动方式尚未冻结。
- 登录页背景图与 logo 的真实来源仍待核实。
- 认证方案尚未在 Session / Token 间定板。
- Web 版数据库恢复仍只有需求，没有正式交互方案。
- 打印主路径尚未在“浏览器打印优先”与“服务端 PDF 优先”之间定板。
- 前端 lint / 单元测试标准命令尚未冻结。
- Alembic 的首次 migration 基线尚未生成。

## 4. 目标总体架构

### 4.1 总体形态
本项目采用前后端分离架构：
- 前端：Vue 3 + TypeScript + Vite + Element Plus + Pinia + Vue Router
- 后端：FastAPI + SQLAlchemy 2.x + Alembic + Pydantic
- 数据库：目标为 PostgreSQL；开发阶段允许临时使用 SQLite，但不作为最终生产形态

### 4.2 分层原则
- 前端负责页面、路由、状态管理、交互、打印视图和体验性权限控制。
- 后端负责认证、RBAC、堂区数据范围过滤、数据聚合、文件存储、图片处理、打印数据组织、数据库备份恢复控制。
- 业务规则以后端为唯一可信来源，前端不承载最终鉴权逻辑。

### 4.3 目录与资源约束
延续阶段 0 目录基线：
- 前端源码：`frontend/src/`
- 前端公共静态资源：`frontend/public/`
- 后端系统静态资源：`backend/app/static/system/`
- 后端上传资源：`backend/app/static/uploads/`

必须保持以下分离：
- 前端构建静态资源
- 系统内置静态资源
- 用户上传资源
- 打印模板资源
- 导出/恢复临时文件

## 5. 前后端边界

### 5.1 前端职责
前端负责：
- 登录页、首页、列表页、详情页、编辑页、打印预览页
- 路由与页面组织
- Pinia 状态管理
- 表单校验、图片预览、权限态显隐
- 打印页面样式与浏览器打印触发
- 与后端 API 的交互和结果展示

前端不负责：
- 最终权限判定
- 最终数据范围过滤
- 文件永久命名与落盘规则
- 密码哈希、凭证签发和安全边界

### 5.2 后端职责
后端负责：
- 登录、登出、登录态管理
- 角色权限校验与堂区范围过滤
- 列表/详情/编辑 API
- 文件上传、图片缩放、命名、存储与访问控制
- 打印数据组织与 PDF 导出扩展能力
- 数据库备份、恢复、校验和审计
- 统一错误响应与日志记录

后端不负责：
- 页面视觉布局
- 浏览器端即时交互体验
- 前端组件级展示逻辑

### 5.3 共同约束
- 所有数据范围判断以后端为准。
- 所有静态资源与上传文件 URL 由统一逻辑生成，前端不得拼接物理路径。
- 所有打印页字段必须来源于统一模板变量字典或统一 API。
- UI 层权限控制仅改善体验，不能代替后端拒绝逻辑。

## 6. 核心专题设计

### 6.1 权限与认证设计

#### 目标
将旧桌面系统中的三角色、七权限和堂区访问范围控制完整迁移到 Web 系统。

#### 现状约束
来源：`src/services/auth_service.py`、`src/services/permission_service.py`、`docs/stage1-requirements-baseline.md`
- 角色：超级管理员、录入员、观察员
- 权限：`user_manage`、`role_manage`、`village_manage`、`household_manage`、`household_view`、`member_manage`、`member_view`
- 数据范围：
  - 超级管理员可访问全部堂区
  - 录入员仅可访问所属堂区
  - 观察员可访问多个授权堂区

#### Web 目标
- 后端实现统一认证与 RBAC 鉴权。
- 后端在查询层或服务层统一执行堂区范围过滤。
- 前端按权限控制菜单、按钮、页面态和只读态，但不替代后端鉴权。
- 搜索、详情、打印必须与列表查询一样遵守堂区范围过滤。

#### 当前待定决策
- 登录态采用安全 Cookie + Session，还是 JWT + Refresh Token。
- 是否支持“记住我”语义，以及保存方式。
- 是否增加登录失败次数限制、过期时间与会话续期策略。

#### 阶段 2 输出要求
- 权限矩阵落地说明
- 登录/登出/续期流程图
- 页面级、按钮级、接口级权限映射说明
- 堂区范围过滤实现位置说明
- 审计日志要求

### 6.2 打印与 PDF 设计

#### 目标
将当前基于 HTML 模板 + Qt 打印的桌面打印能力迁移为 Web 可预览、可打印、可扩展 PDF 导出的方案。

#### 现状约束
来源：`src/views/member_excel_renderer.py`、`src/views/household_excel_renderer.py`、`src/views/household_management_view.py`
- 家庭打印是“家庭页 + 全部成员页”一次合并打印。
- 成员打印支持单独详情页。
- 存在 A3/A4 模板：`doc/a3*.html`、`doc/a4*.html`
- 存在隐藏业务规则：日期值 `1752-09-14` 视为“无”。
- 打印模板内含照片区域，成员照片尺寸语义为 `120x160`。

#### Web 目标
- 保留家庭打印和成员打印两类能力。
- 保留 A3/A4 模板可迁移性。
- 采用“HTML 打印模板 + 浏览器打印”为主路径，PDF 导出作为扩展能力。
- 家庭页在前、成员页逐页追加的分页语义必须保留。

#### 当前待定决策
- 浏览器打印是否作为默认主路径。
- PDF 导出是前端辅助生成还是后端统一生成。
- 打印模板由前端页面维护，还是由后端渲染输出 HTML。

#### 阶段 2 输出要求
- 打印主路径说明
- 模板变量字典
- 分页规则说明
- A3/A4 模板保留策略
- 空日期哨兵处理策略
- 打印验收样张要求

### 6.3 图片与静态资源设计

#### 目标
统一定义内置静态资源、欢迎页资源、登录页资源、成员/堂区上传图片的目录映射、访问规则和降级策略。

#### 现状约束
来源：`docs/stage1-requirements-baseline.md`、`src/views/login_view.py`、`src/views/main_view.py`、`src/views/household_management_view.py`、`src/views/village_view.py`
- 登录背景图与 logo 存在多个候选路径。
- 欢迎页图片已确认存在并已复制到 Web 资源目录。
- 成员照片上传后需统一处理为 `120x160`。
- 堂区图片在桌面版中会做缩放保存。

#### Web 目标
- 登录背景图、logo、欢迎页图片使用前端公共静态资源目录管理。
- 成员和堂区上传图片使用后端上传目录管理。
- 系统内置资源与上传资源物理分离。
- 图片缺失时有明确降级方案，但正式交付不能以“缺图”作为常态。

#### 目标目录映射
- 登录背景图：`frontend/public/images/login/`
- 品牌 logo：`frontend/public/images/branding/`
- 欢迎页图片：`frontend/public/images/home/`
- 上传图片：`backend/app/static/uploads/`
- 系统内置资源：`backend/app/static/system/`

#### 阶段 2 输出要求
- 静态资源目录映射表
- 上传资源命名规则
- 图片访问 URL 规则
- 缺图降级策略
- 历史图片迁移策略

### 6.4 数据库备份与恢复设计

#### 目标
把当前桌面端基于本地文件替换的 SQLite 恢复逻辑，改造成 Web 环境下可控、可审计、可恢复的管理能力。

#### 现状约束
来源：`src/services/database_service.py`、`src/views/settings_view.py`
- 当前桌面版“导出数据库”本质是打开数据库所在目录。
- “还原数据库”流程为：确认风险 → 选择 SQLite 文件 → 校验文件头 → 导入替换 → 提示重启。
- 当前逻辑会在恢复前备份旧数据库文件。

#### Web 目标
- 将“备份/恢复数据库”保留为系统能力，但不照搬桌面端文件管理器交互。
- 恢复操作必须受高权限控制。
- 恢复过程必须记录审计日志。
- 恢复前必须有自动备份策略。
- 是否允许在线恢复、是否需要维护态或重启，需要在阶段 2 正式定板。

#### 当前待定决策
- 是否允许在管理页面上传数据库文件。
- 恢复操作是否仅限超级管理员。
- 恢复时是否要求暂停服务或进入维护模式。
- 未来若切换 PostgreSQL，恢复能力如何重定义。

#### 阶段 2 输出要求
- Web 版备份/恢复流程图
- 权限边界说明
- 校验、备份、回滚和提示规范
- 审计与风险控制要求

### 6.5 数据迁移与初始化策略

#### 目标
为 SQLite → PostgreSQL 迁移、初始数据、历史静态资源和图片迁移提供统一设计输入。

#### 现状约束
来源：`src/models/*.py`、`tests/conftest.py`、`docs/stage1-requirements-baseline.md`
- 当前模型已覆盖用户、角色、权限、堂区、家庭、成员等核心实体。
- 当前测试基座已存在三角色、堂区、家庭、成员样例。
- 当前存在字段口径风险，例如 `Member.id_number` 与模型不一致。

#### Web 目标
- 保留旧系统核心实体与业务语义。
- 对不一致字段先在架构层明确，再进入阶段 3/4 实施。
- 初始化角色、权限、默认管理员、默认堂区策略需要标准化。
- 图片与静态资源迁移要有单独映射策略。

#### 阶段 2 输出要求
- 实体映射表
- 保留字段与调整字段清单
- 初始化数据策略
- 历史图片/静态资源迁移策略
- Alembic 与迁移脚本边界说明

## 12. 风险提示
- 如果认证与权限边界不先冻结，阶段 3 很容易出现前后端各自实现再返工的情况。
- 如果打印主路径不先决定，模板、接口和 UI 设计会反复修改。
- 如果静态资源与上传资源目录不先拆分，部署与访问策略会越来越混乱。
- 如果数据库恢复方案不先限定操作边界，后续实现会带来高风险运维问题。
- 如果阶段 2 只产出概念图而没有标准清单，阶段 3 仍会因为约束不明确而频繁返工。
